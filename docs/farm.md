# Exploit Farm

Farm has its own service catalog and team list. These are independent of Proxy listener configuration: a farm service's port is the destination port on a competition team, not a local reverse-proxy listener.

1. Add a service with its name and destination port.
2. Add each authorized team with its name and numeric IP address.
3. Add an exploit, select its service, and choose Binary, Python, or Bash.
4. Upload a file. For Python/Bash, alternatively select Paste code and paste the source. Click Save exploit once to upload and save its immutable version.
5. Choose a team beside the saved exploit and click Run, or use All selected teams. With no teams selected on an exploit, that means every enabled team. A schedule interval is optional.

IDs and source versions are generated by the UI. Binary uploads execute directly. Python source is saved as `exploit.py`; Bash as `exploit.sh`. Source changes create an immutable new version. Changing a Python version's dependencies requires providing source for a new version. Supported source size is 1 byte–2 MiB. Services/teams and exploit updates use revisions and record their authenticated author in the audit trail. Existing legacy target records remain usable through the API.

## Python and command arguments

Python uses the operator-configured `uv` executable:

```text
uv run --no-project --with requests --with pwntools==4.15.0 python -u exploit.py HOST PORT
```

Dependencies are optional, one package per line or comma separated in the UI. A registry package name or `name==version` is accepted, up to 32 entries. Requirement-file directives, URLs, local paths, and uv command options are rejected. An unpinned dependency follows uv's resolution rules; pin versions when repeatable environments matter. uv uses a private persistent cache. Initial dependency downloads require the host to reach the package registry. Installation errors are visible in stderr.

All runtimes receive the numeric target IP and service port as positional arguments. For example, Python can use `sys.argv[1]` and `sys.argv[2]`; Bash uses `$1` and `$2`. They also receive `HYDRA_TARGET_HOST`, `HYDRA_TARGET_PORT`, `HYDRA_TARGET_ID`, plus `TARGET_HOST` and `TARGET_PORT` aliases. `TARGETS_JSON` is an array of `{id,address,transport}`. Batch mode launches once and supplies `HYDRA_TARGETS_FILE`, a JSON file containing the selected target snapshots. Ordinary per-team mode launches once for each selected team, sequentially within the run timeout.

Example Bash source that only prints its configured destination:

```bash
printf 'Team %s at %s:%s\n' "$HYDRA_TARGET_ID" "$1" "$2"
```

## Host process execution

The operator selects the runner in the private operations JSON. To enable the host runner:

```json
{
  "execution_mode": "host",
  "host_runtime": {
    "uv": "/usr/bin/uv",
    "work_dir": "/var/lib/hydra-core/farm-host"
  }
}
```

Merge these fields with the existing flag/checker settings. The work directory must be absolute, owned by Core's OS user, and mode0700; its parent must exist. The uv path must be absolute. Host jobs are ordinary child processes running as Core's OS user, with the host filesystem and network access permitted to that user and the Core systemd unit. They do not use bubblewrap, a network broker, or per-job cgroups. Core clears inherited environment variables and provides a private working directory, home, and uv cache. Child process groups are killed on timeout, cancellation, or runner interruption. One worker executes at a time; the wall-clock timeout is enforced. The legacy manifest's CPU/memory fields apply to the sandbox runner, not individual host jobs. Core's service-wide limits also include its children.

The previous sandbox runner remains available with `execution_mode: "sandbox"` (the default when omitted). Host mode is an explicit product change requested for this deployment, not an automatic fallback when sandbox setup fails. The API accepts configured team IDs, never a hostname or arbitrary IP supplied to a run request. Queued runs snapshot team IP/service port; disabling or changing an endpoint before launch rejects that queued run. Host programs themselves have ordinary host network access.

## Logs and rotation

Open Logs beside any run. Stdout and stderr are separate readable streams with target labels, state, timestamps, and exit code. The open view refreshes while execution runs. Host output is persisted approximately every300ms. Log payloads are stored as **gzip BLOBs** in Core's private SQLite database; the API decompresses bounded output for display. New logs clear the old plaintext columns. Completed legacy plaintext logs are converted in batches of up to64 records at startup and during periodic retention maintenance. Existing active plaintext records are not modified by that conversion.

Each stdout/stderr stream retains up to1 MiB and marks omitted output. The worker continues draining excess output so a noisy script cannot block on a full pipe. Gzip decompression is bounded independently of compressed size.

Automatic retention keeps completed runs for at most7 days, at most1,000 completed records, and at most64 MiB of total stored compressed output, evicting the oldest when a limit is exceeded. Queued/running runs and the active child are excluded. Retention checks run periodically and after a run finishes. Cleanup is audited; deleted SQLite pages become reusable rather than requiring a database VACUUM during execution.

The UI can clean old runs immediately. The authenticated API also supports:

```text
DELETE /api/v1/farm/runs?older_than_days=7
DELETE /api/v1/farm/runs?older_than_days=0
```

Zero clears completed history immediately while preserving active work. Retry creates a new attempt with the original immutable source/manifest and target snapshot; rotated attempts no longer have a retry source. Run-list cursors now page newest-first by SQLite row position, while service/team catalog cursors remain ID based.

## Reproducible verification

```sh
cd frontend && bun test && bun run build
cd ..
cargo test -p hydra-core --lib
cargo clippy -p hydra-core --all-targets -- -D warnings
cargo build --locked -p hydra-core -p hydra-proxy
python3 tests/e2e/farm_host.py
scripts/check-contracts.sh
```

The host acceptance fixture uses temporary state, a loopback management API, harmless uploaded printing scripts, `/bin/echo`, and Python importing `idna==3.10` through real uv. It verifies service/team selection, direct/all-team execution, output, gzip persistence, flag provenance using a synthetic marker, cancellation, newest-first history, and rotation. It never connects to competition service endpoints.

## Automatic flag queue and Python submitter

Open **Flags → Automatic flag submitter** (also linked from Farm). Enter the competition flag regular expression, paste or upload a UTF-8 Python script, and optionally list Python package names or exact `name==version` pins. Save with submission paused to collect flags without sending them. Enable when the script is ready. Settings are editable, revision checked, persisted in SQLite, and audited; the authenticated author comes from the session. The Farm regex changes immediately for future stdout/stderr scans and survives restart. Proxy defensive scanning retains its separately configured operator pattern.

Every eligible Farm match is deduplicated into the durable flag vault and submission queue, even while submission is paused and even if the legacy `auto_submit_captured` setting is false. Farm target/run provenance is preserved. The queue holds at most 5,000 pending flags; the vault at most 100,000. Existing defensive/own-exposed findings cannot enter this queue. Unknown proxy findings still require explicit triage; this feature does not automatically submit them. Changing the regex does not rescan old run logs.

Enabling or editing starts a 30-second collection window. Every due window snapshots pending eligible flags. A transient child runs the saved Python script through the configured host uv runtime:

```text
uv run --no-project [--with PACKAGE ...] python -u submit.py FLAG1 FLAG2 ...
```

Use `sys.argv[1:]` to read flags. Hydra adds no host/port arguments. Up to 240 flags (at most 60 KiB of flag payload) are passed per call; larger queues use multiple bounded calls in the same cycle. One submitter child runs at a time, independently of the single Farm worker. The script can read `HYDRA_SUBMISSION_BATCH_ID` for the current attempt. Dependency preparation is included in the configured timeout (1–120 seconds, default 20). The runtime uses Core's OS user and the explicit host runtime setting described above; inherited Core secrets are removed from the environment.

The script implements the actual competition checker protocol and interprets its reply. **Exit 0 means every flag in that call was accepted.** A nonzero exit, timeout, unavailable runtime, or interrupted attempt leaves flags queued for retry after at least 30 seconds; ten failed attempts mark them failed. Pausing or editing prevents subsequent chunks from starting with the old revision; a child already claimed may finish. On restart or persistence failure, interrupted claims recover to retry. An external checker may have accepted a flag before a script fails or Core stops, so the checker/script should handle duplicate submissions. Partial acceptance is not inferred from printed output.

The queue, next dispatch time and last batch state/stdout/stderr are visible in Flags. Diagnostic output redacts known flag values and is stored as gzip, with at most 64 KiB per stream. Completed batch logs rotate after 7 days or 500 records; audit records remain. Limits and retries are enforced by Core, independently of the Vue polling interval. Host uv package caches persist between runs and require normal operator disk maintenance.

The generated OpenAPI describes authenticated `GET /api/v1/submitter` and revision-checked `PUT /api/v1/submitter`. No internal gRPC or raw traffic contract changed. Existing private checker adapters remain supported until a Python submitter configuration is saved; a saved paused Python configuration keeps automatic sending paused.

For harmless end-to-end verification with real uv and a pinned dependency:

```sh
cargo build --locked -p hydra-core -p hydra-proxy
python3 tests/e2e/python_submitter.py
```

The fixture starts its own Core/Proxy with temporary databases and loopback-only configuration. It prints synthetic flags, tests collection/acceptance/retry/restart and gzip redaction, and never contacts a competition service or checker. It advances only its own dispatch-clock rows to avoid waiting through each 30-second window.
